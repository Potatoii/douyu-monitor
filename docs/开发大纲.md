# 斗鱼直播间礼物监控系统 - 开发大纲

## 1. 项目概述

### 1.1 项目目标
- 通过 WSS（WebSocket Secure）接入斗鱼 CDN 消息服务器
- 支持**单个或多个直播间**（配置列表指定，每个直播间独立接入）
- 实时接收直播间消息，解析其中的**礼物赠送**信息
- 将礼物数据持久化到 PostgreSQL 数据库
- 同时接入斗鱼 CDN 的全部 6 个端口，避免漏数据，并对重复数据去重
- 日志记录**全部 msg**（规范 JSON 格式、易于查询），数据库只存**去重后的结构化数据**
- 支持礼物价值换算（有礼物信息则换算，无则留空），提供脚本刷新存量数据价值

### 1.2 核心指标
| 指标 | 目标 |
|------|------|
| 数据完整性 | 6 个端口全接入，礼物事件不丢失 |
| 数据准确性 | 无重复记录，幂等写入 |
| 实时性 | 端到端延迟 < 2s |

## 3. 系统架构

```
┌─────────────┐    WSS(443)     ┌──────────────────┐
│  斗鱼CDN服务器  │ ────────────▶ │   WSS 客户端调度器  │
│ 6个端口(0-5)   │                │ (直播间×6条连接并行) │
└─────────────┘                └────────┬─────────┘
                                        │ 原始消息
                                        ▼
                               ┌──────────────────┐
                               │  协议解析器        │
                               │  (msg封包/解包)    │
                               └────────┬─────────┘
                                        │
                      ┌─────────────────┤
                      │                 │ 礼物事件
                      ▼                 ▼
             ┌────────────────┐  ┌──────────────────┐
             │ 日志模块(JSON)  │  │  去重模块          │
             │ 全部原始msg落盘  │  │  (6端口消息合并)   │
             └────────────────┘  └────────┬─────────┘
                                          │ 唯一礼物记录
                                          ▼
                                 ┌──────────────────┐
                                 │  价值换算          │
                                 │  (无信息则留空)    │
                                 └────────┬─────────┘
                                          ▼
                                 ┌──────────────────┐
                                 │  持久化层          │
                                 │  (asyncpg/批量插入)│
                                 └────────┬─────────┘
                                          ▼
                                 ┌──────────────────┐
                                 │   PostgreSQL      │
                                 └──────────────────┘
```

### 3.1 工作流程
1. **接入**：对配置中的每个直播间，分别建立到 6 个 CDN 端口的 WSS 连接（`wss://danmuproxy.douyu.com:850i`，i = 0~5），直播间 × 6 端口并行
2. **认证**：连接建立后发送 `loginreq` 与 `joingroup` 消息，加入直播间弹幕组
3. **接收**：持续接收服务器下发的弹幕数据包
4. **解析**：按斗鱼协议（4 字节长度 + 2 字节类型 + 2 字节加密位 + 4 字节保留位 + 数据体）解包，解析出 `dgb`（礼物）消息
5. **日志**：全部原始消息按规范 JSON 格式记录，可追溯
6. **去重**：以 `消息唯一ID` 为去重键，合并 6 端口重复推送
7. **换算**：通过礼物信息表换算价值（无信息则留空）
8. **存储**：批量写入 PostgreSQL（仅去重后的结构化数据）

### 4.2 各模块职责

| 模块 | 职责 | 关键点 |
|------|------|--------|
| WSS 连接管理 | 管理 6 条 CDN 连接的生命周期 | 自动重连、心跳保活、断线补拉 |
| 协议解析 | 斗鱼消息封包/解包 | 加密字段处理、消息类型识别 |

| 日志模块 | 全部原始消息落盘 | JSON 结构化日志，便于检索追溯 |
| 持久化层 | 去重后的结构化礼物数据入库 | 批量插入、冲突忽略（幂等） |

## 5. 数据库设计

### 5.1 表结构

```sql
-- 礼物事件表（最终落库数据，已去重）
CREATE TABLE gift_events (
    id              BIGSERIAL PRIMARY KEY,
    message_id      VARCHAR(64)  NOT NULL,        -- 消息唯一ID（去重键）
    room_id         BIGINT       NOT NULL,        -- 直播间 ID
    sender_uid      BIGINT       NOT NULL,        -- 赠送者用户 ID
    sender_nickname VARCHAR(64),                  -- 赠送者昵称
    gift_id         INT          NOT NULL,        -- 礼物 ID
    gift_name       VARCHAR(64),                  -- 礼物名称
    gift_count      INT          NOT NULL DEFAULT 1,   -- 赠送数量
    gift_price      INT,                          -- 原始价格（斗鱼币，来自协议）
    total_price     INT,                          -- 原始总价值 = 数量 × 单价
    gift_value      NUMERIC(10,2),                -- 换算价值（人民币，无信息则留空）
    total_value     NUMERIC(10,2),                -- 换算总价值（人民币，无信息则留空）
    receive_uid     BIGINT,                       -- 接收者（如 PK 对象，可空）
    hit_score       INT,                          -- 赠送增加的好感度
    sent_at         TIMESTAMP    NOT NULL,        -- 赠送时间
    received_at     TIMESTAMP    NOT NULL,        -- 服务器收到时间
    port            SMALLINT,                     -- 来源端口（0-5）
    created_at      TIMESTAMP    DEFAULT now()
);

-- 去重键唯一索引
CREATE UNIQUE INDEX idx_gift_events_msg_id ON gift_events (message_id);

-- 常用查询索引
CREATE INDEX idx_gift_events_room_time ON gift_events (room_id, sent_at DESC);
CREATE INDEX idx_gift_events_sender    ON gift_events (sender_uid);

-- 礼物信息表（价值换算依据）
CREATE TABLE gift_catalog (
    gift_id      INT           PRIMARY KEY,
    gift_name    VARCHAR(64)   NOT NULL,
    price_yu     NUMERIC(10,2),               -- 鱼翅价格（可空）
    value_rmb    NUMERIC(10,2),               -- 换算人民币价值（可空）
    updated_at   TIMESTAMP     DEFAULT now()
);
```

### 5.2 表说明
- **消息 ID 唯一索引**是数据库层最终去重保障（配合应用层去重）
- `port` 字段记录来源端口，用于统计各端口数据量、排查漏数据
- **价值换算规则**：写入时通过 `gift_catalog` 换算价值；`gift_catalog` 中无该礼物信息时，`gift_value`/`total_value` 留空（NULL），不影响入库
- **存量数据刷新**：`scripts/backfill_value.py` 遍历存量 `gift_events`，根据最新 `gift_catalog` 回填空白的 `gift_value`/`total_value` 字段，可重复执行（幂等）

## 6. 核心难点与解决方案

### 6.1 6 端口并行接入与去重
**问题**：斗鱼 CDN 6 个端口推送同一直播间的相同消息（互为备份），单端口接入存在漏数据风险，全端口接入则产生 6 倍重复数据。

**方案**：
1. **应用层去重**：每个数据包带 `消息ID`（斗鱼协议字段），维护去重缓存（如布隆过滤器 + LRU 缓存），相同 ID 只处理一次
2. **数据库层去重**：`message_id` 唯一索引 + `ON CONFLICT DO NOTHING` 插入，保证幂等
3. **兜底**：各端口独立记录已处理的最大消息 ID，重连后可从断点继续

### 6.2 心跳与断线重连
- 每 45s 发送心跳包 `mrkl`，超过 90s 无响应判定掉线
- 自动重连策略：指数退避（1s → 2s → 4s ... 最大 60s），重连后重新 `loginreq + joingroup`

### 6.3 加密字段处理
- 斗鱼协议头含加密位字段，部分消息类型需要 XOR 解密（`0x02` 加密标记）
- 解析模块需兼容加密与明文两种数据体

### 6.4 数据写入性能
- 使用 `asyncpg` 连接池 + 批量插入（每批 50~100 条）
- 礼物高峰时避免逐条写入导致瓶颈

### 6.5 日志规范（记录全部 msg，数据库只存去重后的结构化数据）
**要求**：日志中记录全部原始消息，格式规范、易于查询；日志与数据库职责分离。

- **格式**：JSON 单行输出，字段含 `time`（ISO8601）、`level`、`room_id`、`port`、`msg_type`、`msg_id`、`raw_msg`（完整原始消息）
- **分类**：`raw`（原始数据包）、`gift`（解析出的礼物）、`system`（连接/心跳/重连）、`error`（异常）
- **输出**：按天滚动文件（`logs/raw/YYYY-MM-DD.jsonl`、`logs/gift/YYYY-MM-DD.jsonl` 等）
- **易查询**：JSON 单行格式可直接用 grep/jq 检索，例如 `grep '"msg_type":"dgb"' logs/raw/2026-07-31.jsonl`
- **注意**：原始消息量很大，日志模块需异步写入、按天轮转、定期清理（保留天数可配置）

## 8. 测试计划

- **协议解析测试**：用抓包的真实数据包样本测试解包正确性
- **去重测试**：模拟 6 端口推送相同消息，断言只入库一次
- **连接稳定性测试**：长时间运行（24h+），统计断线次数与重连成功率
- **数据一致性测试**：入库数量 = 各端口消息并集（不重复、不遗漏）

## 9. 风险与注意事项

- 斗鱼协议为**非公开逆向协议**，字段可能随版本变化，需预留解析容错
- 心跳/频率限制：过频连接可能被风控，需控制重连频率
- 数据量估算：热门直播间礼物量大，注意数据库写入与存储容量
- 合规性：仅用于个人学习与研究，遵守斗鱼用户协议
